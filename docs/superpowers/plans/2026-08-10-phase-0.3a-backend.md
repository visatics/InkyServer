# Phase 0.3a — Backend (data, API, auth) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move InkyServer's hard-coded device/screen/button config into Postgres, put an auth-scoped management JSON API on top, and keep the frozen `GET /:uuid` device contract behaving exactly as it does today.

**Architecture:** The pure state engine (`src/lib/state.ts`) stops importing module-level constants and instead receives a `DeviceConfig` assembled from DB rows. Its logic is unchanged — only the source of config moves. A repository layer (`src/db/`) owns all SQL; route handlers stay thin. Ownership is enforced in Fastify (the service-role key bypasses RLS), so every `/api` handler resolves the user from a Supabase JWT and scopes queries by `user_id`.

**Tech Stack:** Fastify 5 + TypeScript (NodeNext ESM), Supabase (Postgres + Auth + Storage), `postgres` for SQL, `jose` for JWT verification, `zod` for input validation, `@fastify/multipart` for uploads, sharp for re-encode/EXIF-strip, vitest.

## Global Constraints

- **`src/lib/state.ts` logic must not change.** Signatures change (config becomes a parameter); the body of every function stays byte-identical apart from reading `cfg.*` instead of an imported constant. Acceptance criterion 2 is verified by reading the diff.
- **The device endpoint stays `GET /:uuid` at the root** with the PRD §7 JSON response. Never move or rename it.
- **`:uuid` must validate as a UUID** — non-UUID root paths return 404, so `/favicon.ico` is never treated as a device.
- **Route precedence:** `/api/*` and `/app/*` are static segments and must resolve before the `/:uuid` parameter. No root-level SPA catch-all.
- **Server sends full colour.** No dithering, no palette, server-side. Ever.
- **`uploads` bucket is private; `renders` bucket is public.**
- **Buckets/keys:** source images live at `uploads/<user_id>/<screen_id>/<asset_id>.jpg`; renders stay at `renders/<public_uuid>/<cache_key>.jpg`.
- **No `rss` / `calendar` / `remote`, no SSRF work, no worker queue.** Later phases.
- **Every `/api` handler is owner-scoped.** Cross-user access returns 404 (do not leak existence via 403 on read; use 403 only where the resource is already known to exist and the action is forbidden).
- Providers remain `slideshow` and `debug` only.

## Two reconciliations with the spec

The spec was written against Phase 0.2 as it stood before commit `3a5423d`. Both differences are additive, not contradictory:

1. **`CONFIG_VERSION` is already gone.** `src/lib/cacheKey.ts` currently derives a fingerprint from `{ordinal, config, assets}`. The spec's `updated_at`-based key supersedes this — same intent (edits bust exactly the affected renders), now driven by real rows. Task 3 replaces the fingerprint with timestamps.
2. **`migrations/002_*.sql` does not exist.** Only `001_renders.sql`. The new migration is therefore numbered **`002_web_app.sql`**, not `003`.

```sql
create table if not exists devices (
  id             uuid primary key default gen_random_uuid(),
  user_id        uuid not null references auth.users(id) on delete cascade,
  name           text not null,
  public_uuid    uuid not null unique default gen_random_uuid(),
  width_px       int  not null check (width_px  between 1 and 4096),
  height_px      int  not null check (height_px between 1 and 4096),
  button_count   int  not null default 5 check (button_count between 0 and 5),
  default_screen int  not null default 1,
  updated_at     timestamptz not null default now(),
  created_at     timestamptz not null default now()
);
create index if not exists devices_public_uuid_idx on devices(public_uuid);
create index if not exists devices_user_id_idx on devices(user_id);

create table if not exists screens (
  id               uuid primary key default gen_random_uuid(),
  device_id        uuid not null references devices(id) on delete cascade,
  ordinal          int  not null check (ordinal > 0),
  name             text not null,
  provider         text not null check (provider in ('slideshow','debug')),
  provider_config  jsonb not null default '{}',
  refresh_minutes  int,
  button_overrides jsonb not null default '{}',
  updated_at       timestamptz not null default now(),
  created_at       timestamptz not null default now(),
  unique(device_id, ordinal)
);
create index if not exists screens_device_id_idx on screens(device_id);

create table if not exists device_button_mappings (
  device_id uuid not null references devices(id) on delete cascade,
  button    text not null check (button in ('A','B','C','D','E')),
  action    jsonb not null,
  primary key (device_id, button)
);

create table if not exists slideshow_assets (
  id                uuid primary key default gen_random_uuid(),
  screen_id         uuid not null references screens(id) on delete cascade,
  storage_key       text not null,
  original_filename text,
  position          int not null,
  uploaded_at       timestamptz not null default now()
);
create index if not exists slideshow_assets_screen_pos_idx
  on slideshow_assets(screen_id, position);

alter table renders add column if not exists screen_id uuid
  references screens(id) on delete cascade;
create index if not exists renders_screen_id_idx on renders(screen_id);

-- updated_at maintenance -------------------------------------------------
-- The render cache key folds in these timestamps, so they ARE the cache
-- invalidation mechanism. Triggers keep them honest regardless of which
-- handler performed the write.

create or replace function touch_updated_at() returns trigger
language plpgsql as $$
begin
  new.updated_at = now();
  return new;
end $$;

drop trigger if exists devices_touch on devices;
create trigger devices_touch before update on devices
  for each row execute function touch_updated_at();

drop trigger if exists screens_touch on screens;
create trigger screens_touch before update on screens
  for each row execute function touch_updated_at();

-- An asset change must bust its screen's renders.
create or replace function touch_screen_from_asset() returns trigger
language plpgsql as $$
begin
  update screens set updated_at = now()
   where id = coalesce(new.screen_id, old.screen_id);
  return null;
end $$;

drop trigger if exists slideshow_assets_touch on slideshow_assets;
create trigger slideshow_assets_touch
  after insert or update or delete on slideshow_assets
  for each row execute function touch_screen_from_asset();

-- A device-level mapping change must bust that device's renders.
create or replace function touch_device_from_mapping() returns trigger
language plpgsql as $$
begin
  update devices set updated_at = now()
   where id = coalesce(new.device_id, old.device_id);
  return null;
end $$;

drop trigger if exists device_button_mappings_touch on device_button_mappings;
create trigger device_button_mappings_touch
  after insert or update or delete on device_button_mappings
  for each row execute function touch_device_from_mapping();
```

```ts
import { createHash } from "node:crypto";
import type { DeviceConfig, ScreenConfig } from "./types.js";

/**
 * Render cache key (PRD §4.1). Folds in the timestamps that move whenever
 * config changes, so an edit busts exactly the affected renders and an
 * unchanged screen keeps a stable SHA (the §7.4 short-circuit).
 *
 * Screen identity is load-bearing: two screens can share a provider and
 * would otherwise collide and serve each other's images (fixed in 3a5423d).
 */
export function cacheKeyFor(
  cfg: DeviceConfig,
  screen: ScreenConfig,
  renderState: Record<string, string | number>
): string {
  return createHash("sha256")
    .update(
      [
        cfg.publicUuid,
        cfg.width,
        cfg.height,
        screen.id,
        screen.provider,
        cfg.updatedAt,
        screen.updatedAt,
        JSON.stringify(renderState),
      ].join("|")
    )
    .digest("hex");
}
```

```ts
import postgres from "postgres";

let client: postgres.Sql | null = null;

export function db(): postgres.Sql {
  if (!client) {
    const url = process.env.DATABASE_URL;
    if (!url) throw new Error("DATABASE_URL must be set");
    client = postgres(url, { max: 5, prepare: false }); // prepare:false for pgBouncer
  }
  return client;
}
```

`prepare: false` is required — the Supabase pooler is pgBouncer in transaction mode and rejects prepared statements.

- [ ] **Step 2: Implement, supporting both Supabase key styles**

Supabase projects issue either legacy HS256 (shared `SUPABASE_JWT_SECRET`) or newer asymmetric keys published at JWKS. Support both so the project works whichever it uses.

```ts
import { createRemoteJWKSet, jwtVerify, type JWTPayload } from "jose";
import type { FastifyReply, FastifyRequest } from "fastify";

declare module "fastify" { interface FastifyRequest { userId?: string } }

let jwks: ReturnType<typeof createRemoteJWKSet> | null = null;

async function verify(token: string): Promise<JWTPayload> {
  const secret = process.env.SUPABASE_JWT_SECRET;
  if (secret) {
    return (await jwtVerify(token, new TextEncoder().encode(secret))).payload;
  }
  if (!jwks) {
    jwks = createRemoteJWKSet(new URL(`${process.env.SUPABASE_URL}/auth/v1/.well-known/jwks.json`));
  }
  return (await jwtVerify(token, jwks)).payload;
}

export async function requireUser(req: FastifyRequest, reply: FastifyReply): Promise<void> {
  const header = req.headers.authorization;
  const token = header?.startsWith("Bearer ") ? header.slice(7) : null;
  if (!token) return void reply.code(401).send({ error: "missing bearer token" });
  try {
    const payload = await verify(token);
    if (!payload.sub) return void reply.code(401).send({ error: "token has no subject" });
    req.userId = payload.sub;
  } catch {
    return void reply.code(401).send({ error: "invalid token" });
  }
}
```
